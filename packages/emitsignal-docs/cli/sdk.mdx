The CLI is a thin wrapper over the HTTP API. Everything it can do, the SDK can do —
and the filter grammar is identical in both.

## HTTP API

The raw API follows REST conventions. Authenticate with a bearer token
from `emitsignal keys create`.

<CodeGroup>

```bash Publish
curl -X POST https://emitsignal.com/deploy/prod \
  -H "Authorization: Bearer es_live_••••" \
  -H "Priority: 4" \
  -H "Tags: ci,release" \
  -d "api-gateway → v2.14.3"
# ✓ published → 3 subscribers · 142ms
```

```bash Listen (SSE)
curl -N https://emitsignal.com/events \
  -H "Authorization: Bearer es_live_••••" \
  -H "Filter: priority>=2"
# data: {"ts":"21:52:14","topic":"alerts/prod","priority":5,...}
# data: {"ts":"21:52:22","topic":"ci/web","priority":3,...}
```

</CodeGroup>

## Node / TypeScript

```bash
npm i @emitsignal/sdk
```

```typescript
import { EmitSignal } from '@emitsignal/sdk';

const es = new EmitSignal(process.env.ES_TOKEN);

// Publish
await es.publish('deploy/prod', {
    priority: 4,
    tags: ['ci', 'release'],
    message: `api-gateway → v2.14.3`,
});

// Stream — same filter grammar as the CLI
for await (const ev of es.listen('priority>=2')) {
    console.log(ev.title);
}
```

## Mapping: CLI → HTTP → SDK

Every command maps directly:

| CLI                 | HTTP                  | SDK                         |
| ------------------- | --------------------- | --------------------------- |
| `publish <topic>`   | `POST /<topic>`       | `es.publish(topic, opts)`   |
| `listen --filter`   | `GET /events?filter=` | `es.listen(filter)`         |
| `subscribe <topic>` | `POST /subscriptions` | `es.subscribe(topic, opts)` |
| `keys create`       | `POST /keys`          | `es.keys.create(opts)`      |

<Note>
    The SDK and CLI share the same auth token format (`es_live_…`) and the same filter expression
    grammar. A filter that works in `emitsignal listen` works identically in `es.listen()`.
</Note>
